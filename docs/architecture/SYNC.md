# Синхронизация

1. `Repository.save` изменяет SQLite snapshot, пишет history и outbox в одном
   `BEGIN IMMEDIATE`. UI ждёт только эту транзакцию.
2. Один sync loop обрабатывает очередь последовательно. Следующие операции
   проблемной сущности блокируются, независимые продолжают работу.
3. До первой отправки операция sealed. Её payload и operation_id при повторе
   неизменны. После ответа базовая ревизия назначается следующей неотправленной
   операции этой сущности.
4. Ack сохраняет новые правки, появившиеся во время HTTP-запроса. Они не
   заменяются старым серверным snapshot.
5. Ошибки сети/429/5xx повторяются с bounded exponential backoff и jitter.
   401/403 требуют восстановления сессии, 4xx блокируют операцию до исправления.
6. 409 сохраняет текущую локальную и облачную версии. Выбор пользователя
   создаёт новый operation_id и новую ревизию через `/conflicts/{id}/resolve`.
   При новом конкурентном изменении снова возникает 409. Удаление — такой же
   конфликтующий tombstone, а не автоматическое преимущество удаления.
7. Pull сканирует ресурсы UUID keyset страницами, включая tombstones. Это
   простой полный scan, не инкрементальный timestamp cursor: поздний commit не
   теряется. Серверные данные применяются только при отсутствии локальной очереди.
8. При перезапуске `sending` возвращается в `pending`, sealed payload сохраняется.
9. Выход/удаление аккаунта останавливает sync loop до очистки SQLite и SecureStore.

История и superseded outbox не удаляются при объединении. Обычные tombstones
хранятся без автоматической очистки, пока не спроектирован device acknowledgement
watermark. Полный account deletion удаляет серверные данные физически.

Ограничение v0.1: полный pull имеет линейную стоимость; перед большим объёмом
данных нужен commit-ordered change log. Background sync после закрытия приложения
не реализован. Состояние приложения с SQLite schema > поддерживаемой версии
останавливается без удаления данных.
